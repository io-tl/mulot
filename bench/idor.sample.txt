## Security Audit Report — Root-Me API (ch88 / "Broken Access Control")

**Target:** `http://challenge01.root-me.org/web-serveur/ch88/` → `http://api-broken-access.challenge01.root-me.org/`
**Stack:** nginx fronting a Python/Flask backend (Flask session cookie, Swagger 2.0 API docs).

---

### CONFIRMED — Insecure Direct Object Reference (IDOR) on `GET /api/user/<id>`
**Severity:** High

The API exposes a Swagger-documented `GET /api/user` endpoint, but the server actually honors a path parameter `/api/user/<id>` that is **not** documented in the spec. Any authenticated user can read the full profile (including the private `note` field) of **any** other user by simply iterating the numeric `userid`. The endpoint does not verify that the requested `id` belongs to the caller.

**Exact request:**
```http
GET /api/user/1 HTTP/1.1
Host: api-broken-access.challenge01.root-me.org
Cookie: session=<any valid logged-in user's Flask cookie>
```

**Proof (response body):** The request returned user 1 (`admin`), whose private `note` contained the challenge flag — while I was authenticated only as a freshly created low-priv user (`pentest_user`, id 3):
```json
{"note":"@@@@@@@@@@@","userid":1,"username":"admin"}
```
The same pattern exposes every user (e.g. `/api/user/3` → my own account), confirming horizontal privilege escalation / unauthorized data access.

**Remediation (Python/Flask):** In the `/api/user` handler, derive the target id from the server-side session (`current_user.id`) rather than from client input, or enforce an authorization check (`if requested_id != current_user.id: abort(403)`) before returning the record. Never trust a client-supplied `userid`.

---

### Other observations (no concrete exploit)
- **Session cookie** is Flask-signed (`session=.<base64-zlib>.<ts>.<hmac>`); it carries `_user_id`. It is not forgeable without the secret key, and no disclosure of the secret was observed — not a finding on its own.
- **Mass-assignment lead — NOT CONFIRMED.** Sending `{"note":"…","userid":1}` to `PUT /api/note` returns success, but a follow-up read of `/api/user/1` showed admin's note unchanged (`@@@@@@@@@@@`) — the extra `userid` was ignored and only the caller's own note was updated. No write-side IDOR demonstrated.
- **CORS** is wide open (`Access-Control-Allow-Origin: *`), but with `HttpOnly` session cookies and no credentialed reflection this is low risk here.
- **Missing security headers** (CSP, HSTS, X-Frame-Options) — informational, standard hardening gap.
